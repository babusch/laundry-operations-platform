# Planned-order update API: Development slice

Date: 2026-10-11. The protected API was implemented first; the user subsequently authorized the edit page.

Upgrade note (2026-10-15): live editing has now been confirmed by the user. The subsequent history API adds a nullable audit account-name column; apply that explicit migration before running the new build, following [history setup](ORDER_HISTORY_SETUP.md). No existing audit is renamed/backfilled and no receiving/dispatch behavior changes.

## Scope

`PUT /api/v1/plants/{plantId}/orders/{orderId}/plan` replaces customer, planned receiving date, planned delivery date, customer reference and notes. Only planned orders can be edited. IDs, plant, order number, creation attribution and status cannot be supplied or changed. No schema migration, dependency, service or lifecycle transition is added.

The existing `Start-DevelopmentManagement.ps1 -WithOrders` helper enables the API and edit page after restarting. Existing local orders are not modified by startup. This remains opt-in Development-only at exact loopback HTTPS `https://localhost:7100`, with the same human management session and transactional tenant/plant authorization as creation. No console commands are needed to edit an order.

## Edit through management

Open the bookmarked `/management` page, choose View orders / Visa ordrar, open a planned order, then choose Edit order / Redigera order. The link requires read and planned-edit permission, not merely sign-in. The separate prefilled page shares the create form's native controls, dark theme, Swedish/English resources, inline validation, retained entries and bounded eligible-customer choices. Cancel returns to details without a save. Success returns to current details; unchanged saves do not create a change audit.

The encrypted draft binds the authenticated person, tenant/plant, target order, original version and retry key. These are not editable fields or authorization grants. Current permissions are checked again on requests and within the shared transaction seam. The form POST invokes the same update store used by the JSON endpoint rather than duplicating business rules; the protected original version plays the role of If-Match. Create drafts cannot be used for edits or vice versa.

When another save wins, the page retains the person's entries, displays the latest saved values and disables Save changes. The person must explicitly choose **I reviewed the latest values — keep my entries**, which accepts the displayed version for a new command but does not save. They can then revise their retained fields and deliberately save. A further change before review requires reviewing again; one after review is rejected on save. No automatic merge or silent version refresh is allowed. Conflict review is also translated and retained through language changes. If the latest comparison cannot be loaded, saving remains disabled until it can be reviewed.

After an uncertain commit, original fields are locked for exact retry. A delayed retry can acknowledge the old accepted edit but never revert subsequent changes; redirect loads current details. Forms are not durable offline drafts. Expired sessions/tampered drafts may require reopening; do not claim entries survive every browser/session failure. A later history screen, activation rules and production frontend remain separate work.

## Request and result

- Current `orders.plan.edit` permission is required for exactly one active assignment resolving the path plant to a tenant. Gateway/source credentials cannot authorize editing. Detail reads independently require `orders.read`.
- Send a fresh same-session `X-Management-CSRF`, a nonzero dashed UUID `Idempotency-Key`, and `application/json` bounded to 16 KiB including chunked requests.
- Send `If-Match` copied exactly from the latest detail response's strong ETag (`"order-id:version"`). Exactly one canonical tag is supported; weak tags, wildcard, lists, nonpositive/overflow versions and malformed tags are rejected. Missing header returns 428 `order_precondition_required`; malformed/unsupported header returns 400 `invalid_order_precondition`; a different order ID or stale version returns 412 `version_conflict`.
- All five JSON fields must be present. Use null to clear optional reference or notes; omission on replacement is invalid. Dates use exact YYYY-MM-DD; future receiving and same-day delivery are allowed, but delivery cannot precede receiving. Limits remain 100/2000 characters. Unknown/duplicate fields are rejected. Whitespace normalization is unchanged from creation.
- Success returns 200 with the same public order representation, ETag and detail Location. A changed plan advances the version and stores authenticated before/after audit evidence. A normalized unchanged plan preserves its version/timestamp and adds no change audit, but retains a retry receipt. Order number/ID/creation time remain stable and no number is allocated.
- Order state, audit and receipt commit together through the existing store. Scope, permission and eligibility are coordinated inside that transaction, not trusted from a prior screen check.
- Permission/scope denial returns 403; absent scoped order 404; non-planned order or changed use of a retry key 409. Customer eligibility failures return 400. Authorization/eligibility checks can precede target lookup; these statuses are not an existence probe for another tenant.
- Safe Problem Details contain code/correlation ID, never notes, references, actor subjects, credentials or exception contents. Responses remain no-store. Some authentication/transport responses can have empty bodies.

## Retry and concurrent editing

Keep the same actor, body, If-Match and key after a timeout or 503. A failed response can follow a real commit. An exact authorized retry returns the saved acknowledgement before checking the now-stale version or changed customer eligibility; it never reapplies historical edits. Current human permission is still checked on every retry. Fetch current details afterward, since someone may have edited the order later.

Two different API saves based on the same version cannot both apply. The second receives 412 and must review the latest saved values before deliberately submitting another command. Never silently replace its expected version or auto-merge. The edit form provides this review flow with a readable HTTP 409 conflict page and retained entries.

The OpenAPI document is `apps/cloud/Laundry.Api/Orders/OpenApi/orders.v1.yaml`; its generated TypeScript client types are regenerated rather than handwritten. Run `corepack pnpm --filter @laundry/api-client generate:orders` and the package type check after contract changes.
