## Small first slice

Manually create, list, view, and edit planned service-cycle orders in the management application. Creation does not start receiving. This design follows [Laundry order workflow](LAUNDRY_ORDER_WORKFLOW.md); it does not decide intermediate production states, scheduling, automatic generation, continuous tracking, or item movements.

The management application calls the existing cloud API, which stores these records in cloud PostgreSQL. Order planning belongs to an explicit order module in the modular monolith, separate from raw scan ingestion. No new service or datastore is proposed. Use migrations and a separate management OpenAPI contract to generate the TypeScript client; do not reuse the station-source contract or scan persistence entities.

Remaining technical details below are proposed defaults, including field limits and numbering scope. The planned-order editing rule and initial management permission bundle are approved as recorded here.

## Main table: `orders.service_orders`

This table holds the current order plan, not scanned items or mutable movement counters.

| Column | PostgreSQL type | Required | Meaning |
|---|---|---|---|
| `id` | `uuid` | Yes | Immutable internal order identity, generated by server |
| `tenant_id` | `uuid` | Yes | Company using the platform; derived from authorized context |
| `plant_id` | `uuid` | Yes | Laundry plant; checked against the person's permitted plants |
| `customer_id` | `uuid` | Yes | Laundry customer served by this order |
| `order_number` | `text` | Yes | Server-generated readable number; not the primary key |
| `planned_receiving_date` | `date` | Yes | Planned arrival at the plant; future dates allowed |
| `planned_delivery_date` | `date` | Yes | Planned delivery to the customer, not plant dispatch time |
| `customer_reference` | `varchar(100)` | No | Customer's own reference |
| `notes` | `varchar(2000)` | No | Planning instructions; not operational exception evidence |
| `status` | `text` | Yes | Initially `planned`; no other state is writable in this slice |
| `version` | `bigint` | Yes | Starts at 1; increments when the persisted plan changes |
| `created_at_utc` | `timestamptz` | Yes | Server creation time, represented as UTC |
| `created_by_issuer` | `text` | Yes | Identity provider that authenticated the creator |
| `created_by_subject` | `text` | Yes | Stable identity of that person, not their email/name |
| `updated_at_utc` | `timestamptz` | Yes | Initially creation time, then latest change time |
| `updated_by_issuer` | `text` | Yes | Identity provider for latest editor |
| `updated_by_subject` | `text` | Yes | Stable identity of latest editor |

### Constraints and editing

- Delivery date must be on or after receiving date; same-day service is allowed. No guessed maximum future horizon.
- Dates are calendar values (`YYYY-MM-DD`), not midnight UTC timestamps. Display/calendar interpretation uses the plant's configured timezone; actual receipt/dispatch timestamps remain separate future evidence.
- Plant membership and customer eligibility are server-validated. A customer must belong to the same tenant and be configured for service at this plant. Customer/plant records are prerequisites, not arbitrary caller-provided IDs with no validation.
- Use scoped relational keys/foreign keys where the owning modules permit them so customer/plant references cannot cross tenants. Module-owned eligibility checks remain explicit application contracts.
- `order_number` is unique within tenant and plant. Allocate atomically with a database-backed sequence/counter, never `MAX(number) + 1`. A provisional display format is `ORD-000001`; gaps are acceptable. Numbers cannot be edited or reused.
- Do not make customer and dates a unique key: two genuine orders may have the same customer and dates. Whether additional business warnings are useful remains a later review.
- While `planned`, all five user-entered fields may be edited, including customer. Identity, plant, number, audit attribution, and status cannot be edited through this API.
- Once receiving starts in a later slice, this planning endpoint rejects edits. Later authorized date/instruction changes require their own reviewed rules rather than silently rewriting an active order.
- Proposed indexes: unique scoped order number; `(tenant_id, plant_id, planned_receiving_date, id)`; `(tenant_id, plant_id, customer_id, planned_receiving_date, id)`.
- The initial migration accepts only `planned`. Extend lifecycle constraints through later migrations after transitions are decided, not with speculative states now.

## Supporting tables

### `orders.order_audit_entries`: append-only history

| Column | Type | Meaning |
|---|---|---|
| `id` | `uuid` | Unique audit record |
| `tenant_id`, `plant_id`, `order_id` | `uuid` | Scoped reference to the order |
| `action` | `text` | `order_created` or `order_plan_changed` |
| `order_version` | `bigint` | Resulting version; unique per scoped order |
| `recorded_at_utc` | `timestamptz` | Server recording time |
| `actor_issuer`, `actor_subject` | `text` | Verified human identity |
| `request_id` | `uuid` | Correlates the accepted command with retry protection |
| `before_plan` | `jsonb`, nullable | Previous allowed planning fields; null on creation |
| `after_plan` | `jsonb` | Resulting allowed planning fields |

Audit snapshots include customer, dates, reference, and notes, not tokens or credentials. Treat these as access-controlled business data; do not print their contents in ordinary logs. History is never overwritten by an edit. Persist current state, audit entry, and retry receipt atomically in one transaction. A no-change save returns the existing version without a new change-history entry.

### `orders.command_receipts`: protection against repeated saves

| Column | Type | Meaning |
|---|---|---|
| `tenant_id`, `plant_id` | `uuid` | Command scope |
| `actor_issuer`, `actor_subject` | `text` | Owner of the retry key |
| `idempotency_key` | `uuid` | Client-generated identifier retained for retries |
| `operation`, `target` | `text` | Create/update operation and canonical route target |
| `request_fingerprint` | `text` | Digest of validated normalized fields and edit precondition |
| `order_id` | `uuid` | Resulting scoped order reference |
| `response_status` | `integer` | Original success status |
| `response_body` | `jsonb` | Original accepted response |
| `response_etag`, `response_location` | `text`, nullable | Original success metadata |
| `accepted_at_utc` | `timestamptz` | Server acceptance time |

Unique key: tenant, plant, actor issuer/subject, and idempotency key. Reusing that key for a different operation, target, or normalized request returns a conflict. Concurrent identical requests must converge on one transaction and one receipt. Failed/rolled-back transactions leave no successful receipt.

Retain successful receipts for this initial slice; do not add an arbitrary expiration that could turn an old retry into a duplicate order. A future bounded retention policy needs an explicit retry/recovery contract. Receipt bodies are protected business data, not diagnostic logs.

## Proposed management API

Base path: `/api/v1/plants/{plantId}/orders`.

| Method and path | Purpose | Permission proposed |
|---|---|---|
| `POST /` | Create planned order | `orders.create` |
| `GET /` | List scoped orders | `orders.read` |
| `GET /{orderId}` | Read details | `orders.read` |
| `PUT /{orderId}/plan` | Replace the five editable planning fields | `orders.plan.edit` |
| `GET /{orderId}/history` | Read bounded change history | `orders.read` |

Paths above are relative to the base. Human authentication is required; gateway/source credentials alone never authorize these routes. Derive tenant and actor from verified identity and server-owned memberships, and authorize the path plant. Do not accept tenant, creator, station, or source fields from the client. Exact human login/session transport is a separate identity implementation step; cookie-backed writes require CSRF protection. These routes must stay disabled until human authorization is in place; no unauthenticated development write fallback.

Content-Type: application/json

Required fields: customer and both dates. Optional reference/notes may be omitted or null on creation. Whitespace-only optional values normalize to null; preserve meaningful note line breaks. Reject unknown properties and values over the limits instead of silently truncating them.

### Safe editing and retries

- `PUT /{orderId}/plan` uses the same five fields. Customer/dates are required; reference and notes must each be provided as a value or null, so clearing them is unambiguous.
- Require `If-Match` containing the ETag obtained from the latest read, plus a fresh `Idempotency-Key` for each deliberate save. A retry reuses the exact request, precondition, and key.
- A changed plan returns `200 OK`, the resulting representation, and a new ETag. An unchanged plan returns the existing representation/ETag and still retains a successful retry receipt.
- An identical authorized retry returns the original success status/body/headers, without applying changes again. Resolve an existing successful receipt before checking the now-stale edit precondition. Recheck current authorization on every retry.
- Original retry receipts are historical acknowledgements, not promises that the order is still at that version. Fetch current details afterward; a replay must never revert later edits.
- Missing edit precondition: `428`; stale precondition: `412`; non-planned order or changed use of an existing retry key: `409`. Scope authorization and the state/version check must be enforced within the atomic write, not just before it.

### Reads and errors

- Implemented first list: `GET /api/v1/plants/{plantId}/orders`, current `orders.read`, no filters, limit default 25/range 1–100, stable ascending receiving-date/ID ordering, and an opaque protected tenant/plant/limit/query-version-bound cursor. Returns `{ "items": [...], "nextCursor": null }` when finished, with the public detail fields. Duplicate/unknown query parameters or invalid cursors return 400. Reads make no writes and are no-store; customer deactivation does not hide existing plans. Pagination does not promise a frozen snapshot across edits/inserts. Optional customer, receiving/delivery-date range and status filters remain deferred; future cursors must bind those filters too.
- History uses bounded cursor pagination and stable ascending version ordering. Return action, version, UTC time, permitted actor display information, and allowed planning-field changes; do not expose raw credentials/subjects by default.
- `400`: invalid fields, dates, filters, headers, or customer eligibility. `401`: no valid human authentication. `403`: missing permission or inaccessible requested plant. `404`: an order absent from the authorized scope; do not reveal whether it exists elsewhere.
- Return machine-readable Problem Details with a stable application `code`, field errors where relevant, and a safe correlation ID. The application translates codes into English/Swedish; business values and dates are not translated API strings.
- Database failure never reports success. A timeout or lost response may have happened after commit: retry the unchanged request/key to discover the accepted result rather than creating a second order.
- Logs contain safe identifiers/codes, not notes, customer references, tokens, or full request/receipt bodies.

## Prerequisites, offline boundary, and deferred work

Customer/plant eligibility and human membership/permissions must exist before writes can be enabled. Synthetic development fixtures may bootstrap one customer/plant, but do not substitute for authorization. Final role-to-permission mapping remains a user decision.

This is an online management-planning slice, not an offline receiving workflow. Saving a cloud order does not mean the gateway has received it. Cloud-to-plant order publication, its durable outbox/inbox, version/conflict handling, plant authority after activation, and operator offline authorization need a separate reviewed slice before order-backed scanning is released. Existing local raw-scan acceptance must remain independent of cloud availability.

Do not add receiving/dispatch item rows, quantities, prices, schedules, automatic order creation, continuous accounts, cancellation, completion, or arbitrary status-update endpoints in this slice. These retain their approved product direction or open decisions in the workflow document.

## Implementation acceptance tests

1. Create valid planned orders, including future/same-day dates and null optional fields; reject invalid dates, unknown fields, and oversized values.
2. Multiple genuine orders with the same customer/dates can coexist and receive distinct numbers/IDs.
3. Enforce human permissions and tenant/plant/customer boundaries on every route and retry; reject gateway-only credentials.
4. Identical/concurrent creation retries and lost acknowledgements produce one order, one creation audit, and one receipt; changed requests using the same key conflict.
5. Order/audit/receipt commit together; database outage or transaction failure produces no partial success. Number allocation never produces duplicate scoped numbers.
6. Two edits from the same version cannot overwrite each other. Verify missing/stale preconditions, unchanged saves, and exact update retries after later edits.
7. Planning edits cannot cross activation boundaries when receiving is later implemented; coordinated state/version checks preserve that invariant.
8. Read/history scope, stable ordering, bounded pagination, UTC timestamps, and date-only serialization are covered. Logs and error payloads expose no sensitive planning contents.
