# Order-note visibility: backend foundation

Date: 2026-10-15. Database, backend rules, protected contracts and Development management controls are implemented. Local activation remains separate.

## Management controls (2026-10-15)

Create/edit forms now offer an explicit bilingual Shown/Hidden choice below notes, and current details show the saved choice. A new creation form starts from the plant default shown when opened; that displayed choice is saved explicitly even if the default changes while the form is open. Edit loads the order's saved choice. A create-only account can load its initial default without acquiring general order-read access.

The order list links to `/management/orders/{plantId}/settings`. Current `orders.read` permits viewing the plant default; changing it additionally requires separate `orders.notes.default.edit`. Without that permission the setting is read-only. Saving a default affects future orders, never existing ones. No permission is granted by these pages.

Both forms retain choices across language changes, validation and handled outages. Stale saves show the latest saved value and require explicit review before another deliberate save; review itself writes nothing. An uncertain save locks its exact fields/key for retry, and a delayed retry cannot reapply an older setting or plan. Original v1 protected order drafts remain readable: an older locked retry without visibility preserves omission and its original request identity. Newly issued protected drafts require a valid visibility choice, so removing the field cannot turn a new form into a legacy request. After an old retry, current details provide the actual saved choice.

The controls reuse native keyboard-friendly selects, the existing dark theme, consistent chevron spacing, text feedback and antiforgery/verified-session storage seams. There is no new animation, dependency, migration or production frontend. The live API/database, grants and orders have not been changed. Apply the two prepared migrations before starting the new build, and provision the optional permission only as a separately approved action.

## API follow-up (2026-10-15)

The next authorized small slice adds HTTP/client support, not management editing controls or local activation:

- Order create/update accept optional strict boolean `notesVisibleToOperators`; null, strings, numbers and duplicate fields are rejected. Omit on create to copy the default; omit on edit to preserve the order's stored choice. Explicit false never means “use default.” Existing text-field replacement rules and create/edit permissions remain unchanged.
- Current order detail/list and new receipts include the stored boolean. Immutable old retry bodies may omit it and are returned unchanged. The generated `Order` field is therefore optional; omission means unknown in that receipt. Read current details for the current choice, never infer from today's default.
- History has a separate `OrderHistoryPlan`: recorded visibility is boolean or null for missing legacy evidence. Changed-field values retain the string/null contract, using literal `true`/`false` strings. The read-only history page translates these to Shown/Hidden/Not recorded in English/Swedish, preserving full-width notes and static comparison layout. No historical evidence is rewritten or defaulted to false.
- `GET /api/v1/plants/{plantId}/orders/settings/notes` requires current scoped `orders.read`, returns `{ notesVisibleToOperators, version }` and a strong tenant/plant/version-bound ETag. Unconfigured is false/version 0 without writes.
- `PUT` at the same path requires separate current `orders.notes.default.edit`, verified human session, antiforgery, UUID `Idempotency-Key`, and the exact strong `If-Match` from GET. JSON contains exactly one boolean field and is limited to 1 KiB even with unknown/chunked length. No query parameters are supported. Accepted retries return their original value/version/ETag without reapplying an old default.
- Missing precondition → 428; malformed/wrong-scope tag → 400; stale version → 412; changed key reuse or ambiguous plant assignment → 409; missing session → 401; permission/transport denial → 403; disabled/non-Development → 404; bounded request overflow → 413; non-JSON → 415; storage uncertainty → safe 503. All routes inherit exact Development loopback HTTPS/no-store boundaries, and gateway bearer tokens cannot authenticate them.

OpenAPI and generated TypeScript/client assertions are updated. No further migration, dependency, privilege grant or service is added. The two previously prepared migrations still require explicit local activation before starting the new build. Existing initialization still grants only the original three permissions. Management forms/default-setting page are described above; deliberate permission provisioning, gateway publication and operator scanning remain separate work.

## Storage and behavior

- Required `orders.service_orders.notes_visible_to_operators` boolean. The additive migration sets existing orders to false without changing notes, versions, historical audits or receipts.
- `orders.note_defaults` holds scoped tenant/plant default and version. No row means hidden/version 0; reads create nothing. The first deliberate save persists version 1, even for hidden. Subsequent actual changes increment the setting version; unchanged saves do not.
- `orders.note_default_commands` holds accepted commands: verified actor issuer/subject, request key, expected/result versions, before/after values and UTC time. It serves as append-only administrative audit and exact retry receipt. A distinct no-change command records that accepted request without incrementing the setting version. Rejections write nothing. SQL update/delete/truncate and EF async mutation are rejected.
- New orders copy the current default unless explicitly overridden. Existing orders never inherit future default changes. Ordinary five-field edits preserve the order choice. Explicit overrides in either direction use existing planned-only, permission, version and transaction checks.
- A changed order choice increments its version and records visibility in before/after planning evidence with actor/time. Notes remain intact for authorized management; unchanged choices add no order-change audit.

The owning store accepts the optional named `notesVisibleToOperators` argument, separate from the five-field plan. Omission means inherit on creation, preserve on edit. Request identity distinguishes omission from an explicit choice. Receipt lookup precedes default resolution; changed defaults cannot change an accepted retry. Omitted requests keep the previous fingerprint shape for legacy retries. Delayed setting/order retries return the accepted result without reapplying old values.

Setting writes and order creation share the transaction-bound scoped plant lock. Setting writes require an expected version; order writes retain row/version concurrency protection. The verified-human access adapter binds permission checks to the transaction. No generic last-write-wins behavior is introduced.

## Permissions

`orders.read` allows reading the scoped default. New `orders.notes.default.edit` permits changing it, but is **not** added to the existing management bundle or granted by initialization. A separate identity-access migration allows the permission value without inserting grants. Individual order choices use existing create/planned-edit permissions. Current permission is rechecked before returning saved retries.

## Previous backend-only delivery boundary

The preceding backend-only slice added no HTTP fields/endpoints or client/UI changes. The API follow-up exposes visibility with explicit legacy handling and translated read-only history; management controls are now implemented above. Deliberate default-setting permission provisioning remains separate. Never infer old historical visibility that was not recorded.

Gateway publication remains absent. Its future projection must exclude hidden notes and clear an older working copy on a newer hide update. An offline gateway cannot apply that immediately; append-only cloud evidence is not deleted. No implemented station-side privacy filtering is claimed.
