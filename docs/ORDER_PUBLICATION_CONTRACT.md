## Fields

| Field | Meaning |
|---|---|
| `schemaVersion` | Exactly 1; the format version, not a data revision |
| `tenantId`, `plantId` | Owning scope; a receiver must also match these against its authenticated/configured registration |
| `orderId`, `orderNumber` | Stable internal identity and human-readable number |
| `customer.id`, `customer.code`, `customer.displayName` | Customer identity and labels captured in this published copy; no independent customer master-data synchronization is claimed |
| `plannedReceivingDate`, `plannedDeliveryDate` | ISO calendar dates, not UTC timestamps; delivery cannot precede receiving |
| `status` | Only `planned` is currently implemented; do not invent receiving/completed states ahead of the workflow |
| `notesVisibleToOperators` | Required explicit per-order boolean, never dynamically inherited from the current plant default |
| `notes` | Operator-visible text or explicit null. Hidden always requires null. Visible with no entered note also uses null |
| `version` | Positive cloud-owned revision of the complete published copy within tenant/plant/order; bounded to JavaScript's safe integer range |

All fields are required, and unknown properties are rejected at both object levels. UUIDs must be nonzero. Customer labels use existing 50/200-character limits; note text is at most 2000 characters. Empty/whitespace-only note text is normalized to null before publishing. Examples use deliberately synthetic identities/dates, not today's orders.

## Privacy and version semantics

- A future publisher must construct an allowlisted projection from authorized source records, not serialize a management DTO or persistence entity. Management can read hidden notes; gateway publication must not contain that text, even in internal metadata or logs.
- `notes: null` is an explicit working-copy clearing instruction, not “leave the previous value unchanged.” When visibility changes from true to false, a newer copy must clear the earlier gateway text. The JSON member remains present, but hidden note contents are absent.
- A revision describes the complete projection, including customer labels. A changed customer code/name must eventually produce a newer projection even if the order-row version has not changed. Therefore this `version` is not automatically interchangeable with `service_orders.version`. Durable revision allocation and transactional order-write capture are implemented below; independent customer-change propagation remains a separate step before deployment.
- An exact duplicate revision/payload must be safe to retry; an older revision must not replace a newer copy. Different content under the same scoped revision is an error, not a timestamp tie-break. Working-copy rules are distinct from physical-movement conflict handling.
- An offline gateway retains previously downloaded data, including any previously visible notes, until a newer update arrives. Availability does not prove freshness, and immediate remote note removal is not promised. Removal of working copies does not rewrite append-only audit evidence.

These are receiver/publisher requirements, not behavior implemented or proven by schema validation. UUIDs alone do not establish authorization. A schema cannot check two calendar fields against each other or validate scope against an authenticated gateway. The pure mapper now checks date ordering and consistency against a caller-supplied intended tenant/plant, but gateway authentication and eligibility remain future application-boundary responsibilities.

## Pure cloud mapping

`OrderPlanPublication.From` in the cloud order module constructs a detached, allowlisted immutable output from the order, a customer-module value snapshot, intended tenant/plant and an explicit publication revision. No customer persistence entity is shared. It checks nonempty identities, matching order/customer/tenant/plant, implemented planned status, calendar-date ordering, customer labels and visible-note limits. Errors contain safe fixed codes rather than note text or actor details.

Hidden notes become null before output construction; blank visible notes become null and nonblank visible notes are trimmed. `notes` remains explicitly serialized even under null-omitting serializer settings. Management references, actor data and other persistence fields have no output property. The original order is unchanged, and later source mutations do not alter the mapped copy. Repeated mapping of identical inputs/revision is deterministic; this is not durable retry processing.

The function does not query a database, authorize the caller, evaluate customer active/plant-service eligibility, allocate/check revisions against prior publications, write an outbox, or send anything. A future caller must load a coherent authorized customer/order snapshot and manage publication revisions transactionally; it cannot use this mapper as an authorization bypass. Customer renaming can be mapped with a supplied newer revision, but no automatic rename propagation exists yet.

## Deliberately excluded

Customer reference, management-only text, audit/actor identities, billing details, item/tag data, scan counts and operator sessions are excluded. This format does not grant permission to perform receiving/dispatch or make a raw scan into an operational action. Additional statuses require an explicit schema-version review rather than silently changing v1's accepted states.

This is one order, not a feed/batch. Page cursors, checkpoints, batch IDs, freshness timestamps, gateway inbox/recovery and explicit removals/tombstones remain separate design work. A missing order in a page, an empty response or a failed download must never imply deletion. No automatic date window or order expiry is selected here. Before building synchronization, agree on those rules, permission/scoping and compatibility. HTTP contracts will use OpenAPI/generated clients when HTTP endpoints exist; no handwritten duplicate TypeScript DTO is added now.

## Cloud storage foundation

The user approved transactional publication, explicit initial publication of missing planned-order copies, and no live initial-publication run without separate approval. The primitives, management integration and initial batch runner are implemented in source, not activated in the running application. Independent customer-change propagation remains unimplemented. See [initial-publication setup](INITIAL_ORDER_PUBLICATION_SETUP.md) for the explicit local-only command, provenance and separate activation boundary.

- `orders.publication_heads`: one current working copy, scoped by tenant/plant/order, with complete-copy revision, filtered JSON payload and content fingerprint.
- `orders.publication_outbox`: immutable ready-to-send records, each with a UUID, exact filtered payload, scope, order, revision and UTC recording time. A unique scoped-order/revision index prevents duplicate obligations. Delivery leases, receipts and acknowledgement bookkeeping are not implemented; no row claims gateway synchronization.
- Both tables reference the same scoped order through composite foreign keys. Revisions are positive JavaScript-safe integers; the head's revision is an EF concurrency token. SQL update/delete/truncate triggers and the EF async guard protect outbox evidence. Administrative database privileges are not a technical immutability guarantee.
- `OrderPublicationStorage.StageAsync` requires an explicit owning transaction and tracked order. The caller must acquire the existing scoped order-planning plant lock **before** loading/mutating an order or resolving a coherent customer snapshot. Staging also locks/checks the persisted order version and locks the head; stale loaded orders are rejected. No authorization is granted by passing UUIDs.
- Staging constructs the allowlisted projection, fingerprints content with a fixed comparison revision, and allocates revision 1 or the next revision only when published content differs. Thus hidden management-note edits and customer-reference changes alone do not increase the publication revision. Changed customer labels can create a new revision when a future caller supplies their current snapshot.
- The caller saves and commits its order changes, head and send record in the **same transaction**, after all order changes are finalized. Exceptions must dispose that context/transaction; do not reuse rejected state. A new order and its first publication can be inserted together. Staging itself never commits independently.
- The explicit `onlyIfMissing` mode stages a first copy but leaves existing copies untouched, even if source content has changed. It is the primitive for a future scoped initial-publication runner, not an automatic startup backfill. A runner must enumerate eligible planned orders deliberately and use bounded per-order transactions/current authorization; no date cutoff has been selected.
- Identical content after a lost commit acknowledgement adds no new revision or send record. This primitive is **not** a command-receipt service: future management integration must preserve the existing permission/receipt checks and return historical receipts before staging, so a delayed old command cannot republish historical data. Future customer-change propagation must resolve and coordinate current labels transactionally, not replay stale name snapshots as new versions.
- Previously visible text can remain in older immutable cloud outbox evidence, just as cloud order audit evidence remains. The current head clears it on a hide update; gateway working-copy removal awaits delivery. Retention and transport rules for superseded obligations need explicit review before a sender is built.

Migration `20261016194052_OrderPublicationStorage` is prepared, not applied to the local Compose database. It only adds empty tables, indexes, foreign keys and outbox-protection triggers; no existing order/audit/receipt or permission changes, seeds or publication backfill occur. Do not activate storage-integrated writers before explicitly applying it. No new service, dependency, datastore or transport is introduced, so this follows existing modular-monolith/transactional-outbox decisions rather than establishing a new architecture boundary.

## Automatic staging on management saves

`OrderPlanningStore` now requires a customer publication snapshot for every **new** create/edit command. The verified-human adapter resolves it through the customer module in the existing shared order/membership/customer transaction. `FOR SHARE` holds the eligible customer row (including code/name) and exact active plant-service row until commit. Only a small customer value contract crosses the module boundary, not a persistence entity. Missing/ineligible customer data rejects the command rather than silently skipping publication. Snapshot resolution requires the bound transaction in production composition.

The existing per-plant lock is acquired before customer/order resolution and reused by staging. Order changes, immutable order audit, successful command receipt, publication head and any new outbox entry are saved/committed atomically. A failed publication insert rolls back numbering and all order/evidence changes as well. No external send occurs in the request. The existing storage/transaction failure response remains an uncertain 503 requiring the same request/key, not a new order attempt.

Current permission is rechecked before reading an existing command receipt. Exact accepted retries return that immutable receipt **before** customer resolution or staging, including when the customer is now inactive; revoked human permission still blocks them. Thus a lost response cannot duplicate a publication, and a delayed old create/edit cannot republish old notes or labels after later edits. A different newly accepted command stages current data, not a historical receipt's content.

All new creates stage a first copy. An accepted edit of an older unpublished order (including a deliberate no-change save) stages its first copy. Otherwise only changes to the filtered published content increase publication revisions. Management-only references and hidden-note edits do not. A new no-change order command can refresh changed current customer labels without changing the business order version; this is **not** automatic fan-out when a customer is renamed. Dedicated customer-change propagation still needs implementation. Default-setting saves do not republish existing orders.

This uses the already prepared `20261016194052_OrderPublicationStorage` migration; no further migration, permission, dependency, endpoint or UI control is added. Apply that migration explicitly before restarting the new API build. This turn does not apply it, restart the running service, grant access, or publish local existing orders.
