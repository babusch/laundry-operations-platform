# Development management sign-in: guided setup

Status: backend proof implemented; real Keycloak login/session status and browser local sign-out verified by the user on 2026-10-11. Real timed session expiry remains to be verified.
Date: 2026-10-11.

Account-name addition (2026-10-15): the approved order-history API requests `openid profile` and retains only a validated bounded `preferred_username` as display metadata, never authority or email. The manual client import now lists `profile` as an optional scope; existing clients need that scope attached explicitly before fresh login. Editing import files does not update the live client. See [history setup](ORDER_HISTORY_SETUP.md) for the additive audit migration and activation prerequisites; no secrets/client recreation or extra application permissions are needed. Live inclusion of this claim remains unverified.

This does not create order access or operator station login. It tests only that a person can sign in to the management backend, inspect a safe status, and sign out locally. No order/customer database migration is needed.

## Two different credentials

- **Application client secret:** generated by Keycloak for `management-development`. The .NET backend uses this to identify itself to Keycloak. It is not a person's password.
- **Management demo password:** chosen by you for `management-demo`. You type this into the Keycloak browser login screen. Never use the Keycloak administrator password or gateway secret for it.

Save both in your password manager under distinct development-only entries. Do not paste either into chat, tracked JSON, or `.env.example`. You may also save the application client secret in your ignored private repository-root `.env`; the startup helper reads only that named management setting. It never writes the secret to disk or prints it. Your personal login password does not need to go into `.env`.

## 1. Start the existing identity service

Start Docker Desktop. From the repository root, use the existing private `.env` through normal Compose execution:

```powershell
docker compose -f docker-compose.identity.yml up --detach
./deploy/local/Test-Identity.ps1
```

Wait until the identity test succeeds. Open [Keycloak administration](https://localhost:8443/admin/) and sign in with your existing local administrator. Do not delete or recreate identity database volumes.

## 2. Import the separate management client

In Keycloak, select the **laundry-development** realm, not **master**. Open **Clients**, then **Import client**. Select this public, credential-free file:

```text
C:\Users\jens\Documents\GitHub\laundry-operations-platform\deploy\local\management-development-client.json
```

Import it once. If `management-development` already exists, inspect/update that client rather than creating a duplicate or changing `gateway-development`.

Check its settings:

- Client authentication is enabled (confidential application).
- Standard authorization-code flow is enabled.
- Direct access/password grants, implicit flow, and service accounts are disabled.
- PKCE uses `S256`.
- The only valid redirect URI is `https://localhost:7100/management/signin-oidc`.
- No wildcard web origins or inherited application permission mappings are added.

Open this client's **Credentials** tab. Keycloak generates its client secret; copy it into the application-secret entry in your password manager. Do not regenerate it unless you also update the private value you use when starting the backend.

This file is deliberately separate from the existing realm import. Editing a startup realm JSON does not update an already-imported realm; no identity database reset or gateway reconfiguration is needed.

Keep manual client-import JSON outside `deploy/local/keycloak`: that entire directory is mounted as Keycloak's automatic realm-import directory. Client-only JSON there prevents Keycloak from starting.

## 3. Create a synthetic person account

Still in **laundry-development**, open **Users** and create username `management-demo`. Use only demonstration identity information, with no real employee/customer data. The user must be enabled; leave unnecessary profile fields empty if your realm permits it.

On that user's **Credentials** tab, set a unique development password and save it in your password manager. For this local proof, turn **Temporary** off so no password-change requirement interrupts the first login. Do not assign administrator roles, `scans.ingest`, or machine/service-account privileges.

This user can prove login but has no application-owned plant memberships/order permissions yet. A successful login is not permission to manage orders; those grants are a later slice.

## 4. Save the client secret once and start the cloud API

Stop any cloud API already occupying port 7100 with Ctrl+C in its own terminal. Leave the plant gateway separate.

From a normal PowerShell terminal at the repository root:

```powershell
./deploy/local/Start-DevelopmentManagement.ps1
```

To avoid the prompt on every start, add or update exactly one entry in your private `.env` (not `.env.example`):

```dotenv
MANAGEMENT_CLIENT_SECRET='paste-the-current-management-development-client-secret-here'
```

Replace the placeholder locally with the **application client secret from step 2**, not your management-demo password. Save the file. Do not share its contents with an agent. The repository's `.gitignore` excludes `.env`; that does not encrypt the file or prevent filesystem access by local tools. Agent rules continue to prohibit inspecting it without specific credential-investigation authorization.

Loading priority is explicit `-PromptForSecret`, otherwise the `MANAGEMENT_CLIENT_SECRET` process environment variable, then the same key in the repository-root `.env`, then a hidden prompt if none is configured. Thus a stale process variable can override the file; remove that one process setting or use `-PromptForSecret` when diagnosing it. The optional `-EnvFile` parameter selects a different Development file; automated tests use only synthetic temporary fixtures and never the actual private file.

The helper supports bare and literal single/double-quoted one-line values, optionally followed by comments. It does not evaluate commands, interpolate variables, expand escape sequences, or import other dotenv settings. Duplicate management entries and malformed quoting fail safely rather than choosing an ambiguous value.

If prompted, paste the **application client secret**, not the user's password. Input is hidden. The helper temporarily sets the backend's management configuration, starts the cloud API, and restores prior process settings when it exits. Credentials in plain local files/process memory/environment remain accessible to sufficiently privileged local tools: this is Development convenience, not production secret management.

Before starting the API, the helper checks that exact pasted secret with Keycloak's PAR endpoint over trusted HTTPS. It prints only acceptance or a safe failure message; failed verification stops startup. It also sets the fixed Development authority/client ID for this run, restoring their previous process settings afterward. No provider response URI or credential is displayed. The check creates only a short-lived unused authorization request, not a user login or business action. This helper supports both Windows PowerShell 5.1 and PowerShell 7; it does not use newer-only static crypto APIs or `-SkipHttpErrorCheck`.

ASP.NET Core does not automatically read `.env`: this helper explicitly bridges the single management key into its backend setting. Keep the password-manager entry as a backup. To deliberately ignore saved values and use the hidden prompt:

```powershell
.\deploy\local\Start-DevelopmentManagement.ps1 -PromptForSecret
```

Combine it with `-WithAccess` or `-WithCustomers` when checking those features.

The normal `dotnet run` command leaves this feature disabled by default. Enabling it without a private client secret fails startup with a safe configuration error. Production and Staging never register the proof routes even if the setting is enabled.

## 5. Verify real login

Open [management login](https://localhost:7100/management/login). Keycloak should ask you to sign in. Enter `management-demo` and the person's password from step 3.

After successful login, the browser returns to `/management/session` and displays:

```json
{"authenticated":true,"orderAccessEnabled":false}
```

This plain JSON is intentional: no management UI has been added. Tokens, raw identity claims, and credentials are not displayed. A different browser/profile without that login returns HTTP 401 at the session route. The cookie session lasts at most 15 minutes, does not slide/refresh automatically, and has no persistent browser expiry; browsers may restore session cookies when restoring a session, but the server-side time bound still applies.

The backend uses the ordinary framework OpenID Connect flow. Access/refresh/ID tokens are not retained in the management authentication ticket. It records only stable issuer/subject identity and server-owned interactive-login provenance inside the protected cookie. These are not exposed by session-status JSON.

## 6. Verify local sign-out

There is no sign-out button yet. In the signed-in browser tab, open the browser's developer console and run this development-only snippet:

```javascript
const csrf = await fetch('/management/antiforgery').then(response => response.json());
const result = await fetch('/management/logout', {
  method: 'POST',
  headers: { [csrf.headerName]: csrf.requestToken }
}).then(response => response.json());
console.log(result);
```

Expected result: `signedOut: true` and `identityProviderSessionEnded: false`. Reload `/management/session`: it should return HTTP 401. This endpoint requires the current session and its antiforgery token; a GET or a tokenless POST cannot sign you out.

Sign-out removes this application's cookie locally and works even when Keycloak is unavailable. It does not terminate the Keycloak SSO session or revoke a copied cookie server-side; an existing copied ticket remains bounded by its 15-minute lifetime. A new `/management/login` explicitly requests fresh authentication rather than silently reusing the provider session. Broader sign-out/revocation needs later design.

## Failure feedback

- Login initiation rejected by Keycloak returns 502 and `management_identity_rejected`. For example, Keycloak reports `invalid_client_credentials` when the application's supplied client secret is not accepted. Stop the API with Ctrl+C, copy the current secret from **laundry-development → Clients → management-development → Credentials**, and rerun the helper with that secret. Do not use the demo-user password, administrator password, or gateway secret. No secret needs to be shared with an agent. Pushed Authorization Requests (PAR) remains enabled when the provider advertises it; this failure must not trigger an insecure fallback.
- Login initiation with an unavailable identity provider returns 503 and `management_identity_unavailable`; process liveness remains independent.
- An invalid/interrupted callback returns 400 and `management_login_failed`, without exposing token/identity details. Restart from `/management/login`; do not copy callback URL parameters into chat.
- Wrong client secret, disabled user, or Keycloak required actions may interrupt login. Check public settings and the browser's safe error first. Do not share passwords, expanded Compose configuration, tokens, or authentication cookies.
- Only the exact HTTPS origin `https://localhost:7100` and a loopback source address may use these routes/callbacks. HTTP, other hostnames/ports, and remote callers are rejected. This is not ready for LAN or production access.
